# 多平台发布流程

## 1. 建立发行范围

仅规划时不运行环境doctor或探测钥匙串/证书/登录态；输入是本项目事实，不是本机其他项目的身份。到第3阶段实际构建时才检查必要工具链，证书存在不能证明当前账号资格。

首次交付采用发行模板和release-self-check.md，不等验收反馈才补齐。APP源码版本与专家版本独立；地区逐行列出，不能把中国区资格放进美国行的“同上”。原生鸿蒙工具为DevEco Studio，Android包不能作为其兼容证明。

确认APP功能、系统、国家/地区、语言、主体和已有包/源码。读取平台目录筛选首批渠道，给出适配理由、缺项及不适用渠道。先做一个可验证的首发渠道，再复用共有材料扩展；用户指定并行渠道时分别推进，不需要重复许可。

## 2. 准备共用与差异材料

共用：名称、简介、功能描述、支持联系方式、隐私政策、数据收集/第三方SDK实际清单、版权归属、图标、截图、版本说明、测试方法。必须与真实产品一致，不能生成虚假隐私声明或不可用的审核账号。

差异：语言、商店字数/尺寸、年龄和内容评级、目标国家、支付/IAP/广告、数据安全声明、账号删除能力、地区与类目资质。涉及儿童、金融、医疗等按实际功能进一步核查。上传前检查公开链接可用性与素材隐私，不上传密钥/证件。

## 3. 构建与运行

沿用开发四阶段；逐目标记录源码版本、构建命令、工具链、包标识、版本号、签名归属、产物路径与SHA-256。验证签名、安装/启动、主要流程和旧版升级数据。没有目标设备或工具链就注明未验证。不能用Android包代替iOS/鸿蒙构建，不能用Gate通过替代真机或商店要求。

## 4. 上传与提审

先核本次授权的应用、商店、版本、国家/地区、测试/生产轨道、价格和上线方式。用户明确授权覆盖当前操作时继续；仅要求计划或本地打包则交付待提交候选。

优先官方可用API/CLI；不具备已验证适配器时用宿主获授权浏览器或给出具体控制台步骤。先读取现有应用和版本，避免重复创建。上传、提交审核、正式发布分别记录动作和回执；网络超时先查状态，不盲目重试。验证码、实名与支付由用户本人处理。

## 5. 审核与发行

| 状态 | 最低证据 | 下一步 |
|---|---|---|
| 待准备 | 计划/缺项清单 | 准备账号、材料、构建 |
| 受阻 | 具体缺项或平台错误 | 指明责任人及解除条件 |
| 待提交 | 候选包与材料验证记录 | 核授权后上传/提审 |
| 审核中 | 平台确认提交的回执/控制台状态 | 按官方机制查询，不高频轮询 |
| 被拒 | 实际拒绝原因和版本 | 修复、复验并按授权重新提交 |
| 已批准 | 平台审核通过证据 | 核发布方式/地区/时间 |
| 已上线 | 目标地区实际商店页及可获取版本证据 | 监测崩溃、反馈和后续更新 |

上传成功不能直接变为已上线；自动发布需核实际生效。一个平台通过不代表其他通过。不能根据CLI退出码或本地计划自动提升发布状态。

## 6. 更新与回退

保存上一版本、数据兼容性记录、渠道包与变更说明；灰度、暂停和下架能力以平台实际支持为准，不承诺可即时回退已安装版本。拒审修复只重做受影响检查，版本变化后重新校验产物与材料。跨商店保持独立状态，发现一个失败不抹掉其他真实成功结果。

最终交付：逐平台状态表、包与素材、实际执行证据、未执行项、本人下一步；不能用“全球发布完成”概括部分渠道。
